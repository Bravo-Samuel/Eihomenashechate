Make existing WEB notifications reliable, secure, idempotent, timezone-aware, and safe for production deployment.

==================================================
PHASE 2 — SCHEDULER RELIABILITY
==================================================

Fix scheduled notification processing so it is safe under Replit Autoscale.

Requirements:

1. Make scheduled processing atomic.

2. Prevent two API instances/processes from processing the same scheduled item simultaneously.

3. Use PostgreSQL-backed locking/claiming appropriate for the existing schema.

4. Add durable idempotency.

5. A scheduled notification must have a durable processing state.

Use states appropriate to the existing architecture, for example:

pending
processing
sent
failed

Do not blindly add duplicate tables or systems if the existing schema can support the requirement.

6. NEVER permanently remove a scheduled item before successful delivery.

7. If delivery fails:
   - preserve the scheduled item/state
   - record the failure
   - increment retry information
   - retry safely according to a bounded retry strategy

8. Prevent infinite retries.

9. Make processing safe if the API restarts halfway through delivery.

10. Ensure a notification cannot be delivered twice because of overlapping scheduler ticks.

11. Ensure multiple Autoscale instances cannot claim the same notification.

12. Make scheduled announcements use the SAME actual scheduler/delivery path.

Do not leave scheduled announcements in a table that is never consumed.

==================================================
PHASE 3 — TIMEZONE CORRECTNESS
==================================================

Server-generated scheduled notifications must respect the subscriber's intended timezone.

Do NOT use only:

new Date().getHours()

or server-local time.

Inspect how subscriber location/timezone is already stored.

Use the existing timezone information wherever available.

Requirements:

- 08:00 means 08:00 in the subscriber's timezone.
- 09:00 means 09:00 in the subscriber's timezone.
- Weekly reminders must use the subscriber's local day/time.
- Holiday/Yahrzeit notifications must be evaluated using the intended user's timezone.
- Avoid duplicate delivery when daylight-saving transitions occur.
- Do not break users in India or other non-server timezones.

Use a reliable timezone-aware implementation compatible with the existing project dependencies.

==================================================
PHASE 4 — WEB PUSH SECURITY
==================================================

Fix notification-click security.

The service worker must only navigate to safe Menashe destinations.

Requirements:

- HTTPS in production.
- Same-origin only.
- Reject external notification URLs.
- Reject javascript/data/blob URLs.
- Safely handle malformed URLs.
- Preserve relevant internal paths such as:
  /notifications
  /yahrzeit
  /memorial
  /calendar
  etc., according to the existing application routes.

If the notification does not contain a valid destination, use a safe default application route.

Do not allow a push payload to turn into an arbitrary external redirect.

==================================================
PHASE 5 — PUSH SUBSCRIPTION OWNERSHIP
==================================================

Prevent an existing browser push endpoint from being reassigned to another Clerk user.

Requirements:

- The authenticated Clerk user owns the subscription.
- An existing endpoint must not silently change ownership.
- Preserve legitimate re-registration by the same user.
- Reject or safely handle an endpoint already belonging to another user.
- Use a collision-resistant subscription identity.
- Enforce appropriate database uniqueness for the full endpoint.

Do not trust client-supplied userId.

Continue deriving ownership from authenticated Clerk context.

PHASE 7 — VAPID CONFIGURATION
==================================================

- VAPID_PUBLIC_KEY exists
